# 不明白播客知识库网站设计规范

日期：2026-07-14

状态：已完成交互设计确认，等待书面规范复核

## 1. 项目目标

建设一个公开访问、低成本、可持续更新的《不明白播客》知识库网站。网站把节目、嘉宾、正式推荐作品、版本信息和作品关系组织成可检索、可追溯的数据，而不是把内容继续堆在表格或长文章中。

V1 必须实现以下目标：

1. 按节目期数浏览嘉宾、主题和正式推荐作品。
2. 按作品浏览原名、创作者、中文译本、版本资料和证据状态。
3. 每条推荐能够追溯到官方节目页、文字稿或明确的“嘉宾推荐”栏目。
4. 每部作品展示同作者作品和带有明确理由的相似作品。
5. 播客出现新一期后，节目基础信息可以自动同步，风险较高的推荐拆分和版本评价经过核验后再公开。
6. 封面和海报采用权利感知的多源策略，首图优先使用可核验的原版。
7. 低访问量阶段不产生固定服务费用，外部免费额度耗尽时网站仍能提供已有内容。

## 2. 非目标

V1 不包含以下功能：

- 用户注册、登录、收藏、评论和个性化推荐。
- 在线后台管理系统。
- 在浏览器中实时调用第三方书籍、影视或 AI API。
- 自动生成未经来源支持的翻译质量结论。
- 批量复制来源规则不允许镜像的封面或海报。
- 把节目中顺带提及的作品自动当作正式推荐。
- 依赖单一商业 API 维持页面基本可用性。

内容修订通过版本库中的数据文件、审核队列和拉取请求完成。需要动态协作或用户账户时再单独设计后台系统。

## 3. 已确认的设计决策

| 领域       | 已确认方案                                                     |
| ---------- | -------------------------------------------------------------- |
| 首页       | 双入口首页，节目更新与作品探索并重                             |
| 作品详情页 | 证据优先，先展示推荐出处，再展示版本和关联作品                 |
| 更新发布   | 分层发布，低风险节目字段自动公开，高风险内容核验后公开         |
| 相似推荐   | 可解释的混合模型，硬关系与相似排序分开                         |
| 外部数据   | Open Library、TMDB、Wikidata、Commons、Workers AI 的开放混合栈 |
| 图片       | A+ 权利感知多源图片层，首图优先可核验原版                      |
| 部署       | 静态优先，Cloudflare Workers Static Assets                     |
| 自动化     | GitHub Actions 定时同步、校验、构建和发布                      |
| V1 数据库  | 不使用运行时数据库，构建产物和静态索引是公开站点数据源         |

## 4. 当前数据基线

当前结构化输入为 `work/bumingbai_structured.json`，包含：

- 237 条节目记录。
- 423 条推荐记录。
- 节目标题、日期、官方链接、文字稿链接、推荐原文和解析状态。
- 推荐作品标题、原名、创作者、媒介类型、来源链接和部分中译本信息。

这份 JSON 是迁移输入，不是网站的最终领域模型。它仍有标题拆分错误、创作者错位、同一作品重复和元数据状态不一致等问题。网站不得直接把所有扁平记录视为已经核验的事实。

迁移过程必须保留 `raw_entry`、官方来源 URL 和现有核验状态。错误修正通过新增规范化记录完成，不覆盖无法重建的原始证据。

## 5. 总体架构

V1 采用静态优先架构：

```text
官方 RSS / WordPress API / 文字稿
                 ↓
          抓取与原始快照
                 ↓
       解析、规范化、证据校验
                 ↓
  Open Library / TMDB / Wikidata / Commons
                 ↓
     作品消歧、图片选择、关系计算
                 ↓
       Zod 校验后的规范化 JSON
                 ↓
       Astro 静态页面与搜索索引
                 ↓
 Cloudflare Workers Static Assets
```

技术选择：

- Astro 负责静态页面生成和按需客户端组件。
- TypeScript 负责网站、同步脚本和领域逻辑。
- Zod 是数据契约的单一事实来源，TypeScript 类型从 schema 推导。
- 静态搜索索引在构建阶段生成，不依赖运行时搜索服务。中文字段生成单字前缀和双字词元，拉丁文字按规范化单词和前缀索引。
- Cloudflare Workers Static Assets 托管站点。
- Hono 仅在未来确实需要动态端点时引入，V1 不为单一用途提前增加 Worker API。
- Cloudflare D1 在 V1 中不启用。只有需要用户账户、在线审核、多用户写入或数据规模导致静态构建不可接受时才重新评估。

第三方 API 只在同步或构建任务中调用。浏览器只读取本站生成的页面和 JSON，因此外部服务故障不会让已发布内容消失。

## 6. 领域模型

所有公开实体使用稳定 ID。展示 slug 可以改变，实体 ID 不随标题、译名或 URL 改变。外部 ID 只能作为标识之一，不能代替本站实体 ID。

核心实体如下：

| 实体                   | 责任                                               |
| ---------------------- | -------------------------------------------------- |
| Episode                | 一期节目、发布日期、嘉宾、主题、官方链接和同步状态 |
| Person                 | 嘉宾、主持人、作者、导演、译者等人物               |
| Work                   | 抽象作品，例如一本书、一部电影或一套纪录片         |
| Edition                | 书籍版本、译本、影视地区发行版本                   |
| RecommendationEvidence | 某人在某期节目推荐某作品的证据                     |
| ImageAsset             | 图片来源、对应版本、许可、用途、尺寸和失效状态     |
| WorkRelation           | 同作者、同系列、同一期、人工策展和相似作品关系     |
| ProviderRecord         | 外部服务记录、外部 ID、抓取时间和原始响应摘要      |
| ReviewIssue            | 无法自动确认的字段、候选值、原因和处理状态         |

关键枚举：

```ts
type VerificationStatus =
  "verified" | "partially_verified" | "pending_verification" | "rejected";

type PublicationStatus = "public" | "withheld";

type ImageRole = "hero" | "edition" | "fallback";

type ImageHandling = "hotlink_only" | "mirror_allowed" | "display_prohibited";
```

每个可争议字段都必须能关联来源。来源至少包含 URL、来源类型、抓取或核验时间和证据摘录的定位信息。没有来源的翻译质量只能是 `pending_verification`，公开文案显示“未核实”。

## 7. 内容可信度规则

推荐作品只有满足以下条件才能公开为正式推荐：

1. 来源是官方节目页、官方文字稿、官方 RSS 描述或官方明确链接的内容。
2. 原文存在“嘉宾推荐”等明确语义，或者推荐关系由人工核验。
3. 推荐人与作品的对应关系可以确认。无法确认推荐人时可以公开作品，但必须显示“推荐人未确认”。
4. 作品拆分通过 schema 校验，且没有把一个条目错误拆成作者或多个作品。
5. 原始推荐文本和来源 URL 被保留。

翻译质量规则：

- 作品总评分不能作为翻译质量评分。
- “优秀”“一般”“存在删节”等判断必须有针对具体译本或译者的可靠来源。
- 只有中译本存在不等于翻译质量已核验。
- 多个中译本分别建 Edition，不把不同译者和出版社混成一条记录。
- 无可靠证据时显示“未核实”，不使用模型补写结论。

## 8. 分层同步与发布

GitHub Actions 每 6 小时运行一次，也支持手动触发。同步流程如下：

```text
发现官方更新
    ↓
保存原始响应与抓取时间
    ↓
比较已有节目和内容哈希
    ↓
解析节目基础字段与推荐候选
    ↓
分别进入低风险和高风险通道
```

低风险字段包括：

- 节目编号、标题、发布日期和时长。
- 官方节目页、音频和文字稿链接。
- 官方明确列出的嘉宾姓名。

低风险字段经过 schema、重复项、链接和构建检查后，由自动拉取请求合并并部署。自动合并只允许触及低风险数据文件，不能混入作品消歧、译本或评价变化。

高风险字段包括：

- 一段文字中包含多少部作品。
- 作品标题、原名、作者或导演的消歧。
- 推荐人与作品的对应关系。
- 中译本、译者、出版社、删节和翻译质量。
- 图片是否对应正确版本及其权利状态。

高风险候选写入审核队列和单独的拉取请求，不自动进入公开作品数据。公开节目页可以显示“本期推荐资料正在核验”，但不展示未经确认的候选标题。

同步失败时保留最后一次成功构建。部分抓取结果不得覆盖完整旧数据。连续失败在 GitHub Actions 中产生失败状态和可下载日志，不向公开页面发布半成品。

## 9. 外部 API 与缓存策略

外部数据采用开放核心混合栈：

| 数据类型         | 首选来源                                   | 用途                                 | 降级路径                      |
| ---------------- | ------------------------------------------ | ------------------------------------ | ----------------------------- |
| 书籍与版本       | Open Library                               | 作品、版本、作者、ISBN、封面候选     | Wikidata、人工核验            |
| 影视             | TMDB                                       | 作品、演职员、原始发行信息、海报候选 | Wikidata、Commons、文字占位图 |
| 跨库标识         | Wikidata                                   | 多语言名称和外部 ID 对齐             | 现有官方来源                  |
| 开放图片         | Wikimedia Commons                          | 许可明确的图片                       | 来源 API、文字占位图          |
| 文本向量         | Workers AI `@cf/qwen/qwen3-embedding-0.6b` | 中英文主题相似度的构建期信号         | 结构化规则推荐                |
| 人工书目核验线索 | Google Books                               | 个别疑难版本的人工比对               | 出版社、图书馆或官方书目页面  |

规则如下：

- API 密钥只存在于 GitHub Actions 或 Cloudflare 环境变量，不写入仓库，不暴露给浏览器。
- 保存规范化结果、外部 ID、抓取时间和必要的响应摘要，不无期限保存来源条款禁止缓存的原始内容。
- 构建优先使用最近一次已核验缓存。外部 API 暂时失败时不删除已有元数据。
- 新作品没有可用缓存且外部 API 失败时，只发布已核验的节目证据，不伪造补充元数据。
- Workers AI 免费额度不足时跳过本次向量更新，规则推荐继续工作。
- Google Books 不成为生产页面的唯一数据源。
- TMDB 仅按其非商业开发者条款和署名要求使用。网站转为商业用途前必须停止自动取用并重新确认许可。
- Wikidata 结构化数据与 Commons 媒体分开处理。Commons 图片必须逐文件保存许可证和署名信息，不能因为 Wikidata 数据采用 CC0 就推定图片也采用 CC0。

## 10. A+ 图片策略

图片资产层保存多个候选，不让页面直接绑定单一第三方 URL。每条 ImageAsset 至少记录：

- 对应作品和具体版本。
- 来源提供方、来源页面和外部 ID。
- 原始图片 URL 和可用尺寸。
- 图片角色：首图、版本图或备用图。
- 版本角色：原版、中译本或地区发行版。
- 许可、署名文本和商业使用复核状态。
- 处理方式：仅直连、允许镜像或禁止展示。
- 清晰度、长宽比、最后验证时间和失效状态。

首图选择顺序：

1. 可核验的原版封面或原始发行海报。
2. 同一原版的其他官方图片。
3. 准确匹配的中文版本图片。
4. 其他可核验的正式版本图片。
5. 本地生成的文字封面或海报。

“原版优先”不是权利和质量豁免。候选必须同时满足来源可核验、允许展示和清晰度达到最低阈值。书籍原版依据原文书名、首版年份、首版出版社和版本标识判断。影视原版依据原始发行地区、语言和发行记录判断。

首图最低质量规则：

- 源图片长边至少 600 像素，且没有明显压缩损坏、错误裁切或水印遮挡主体。
- 图片不得被放大到源尺寸的 1.5 倍以上。
- 未达到首图阈值的原版图片仍可保留在版本图库，但不能占用首图位置。
- 列表缩略图长边最低 240 像素。低于该值时使用本地文字封面。

首页卡片和作品详情页头图使用首图。中译本、港台版、修复版和其他地区海报进入版本图库，不会被丢弃。

性能策略：

- 列表使用来源提供的小尺寸，详情页按需加载大图。
- 使用固定宽高比、原生懒加载和来源域名预连接。
- 仅对明确允许镜像或自行制作的图片写入 R2，并生成 WebP 或 AVIF 衍生尺寸。
- 仅可直连的图片继续使用官方 CDN。
- 图片加载失败时依次切换同一原版备用来源、已核验版本图和本地文字封面。
- 详情页提供图片来源、对应版本、许可和最后验证时间。

## 11. 作品关系与推荐模型

同作者、同导演、同系列和同一期是确定关系，不参与模糊相似度推断，单独展示。

相似作品采用可解释的构建期排序。基础权重如下：

| 信号             | 权重 | 说明                                             |
| ---------------- | ---- | ------------------------------------------------ |
| 主题与关键词     | 35%  | 结构化标签为主，向量相似度最多占该项 10 个百分点 |
| 同一期共现       | 20%  | 同一嘉宾推荐列表或同一期节目中共同出现           |
| 体裁与媒介       | 15%  | 书籍类型、影视类型和内容形式                     |
| 时代与地域       | 10%  | 作品涉及的时代、国家、地区                       |
| 嘉宾或推荐人重合 | 10%  | 被同一人或相似嘉宾群体推荐                       |
| 人工策展         | 10%  | 经过版本库审查的专题关系                         |

每张相似作品卡片显示主要原因，例如“同为文革口述史”“同一期由杨樱推荐”或“主题均为流亡与记忆”。不得只显示一个不透明的百分比。

质量约束：

- 排除当前作品本身和重复版本。
- 硬关系和相似关系分区显示。
- 至少有一个可解释的非向量信号才能公开推荐。
- 数据不足时减少推荐数量，不用低质量结果填满固定名额。
- 人工策展可以提升或排除结果，但改动必须进入版本控制。

## 12. 信息架构与页面

公开路由：

| 路由                  | 内容                                                   |
| --------------------- | ------------------------------------------------------ |
| `/`                   | 双入口首页、全站搜索、最新节目、最近新增作品和主题入口 |
| `/episodes/`          | 按时间、嘉宾、主题和核验状态浏览节目                   |
| `/episodes/[slug]/`   | 节目信息、嘉宾、官方链接、推荐证据和作品列表           |
| `/works/`             | 按媒介、主题、年代、创作者、中译本和核验状态浏览作品   |
| `/works/[slug]/`      | 作品资料、推荐出处、版本图库、同作者作品和相似作品     |
| `/people/[slug]/`     | 人物身份、参与节目、创作作品和推荐作品                 |
| `/topics/[slug]/`     | 主题说明、相关节目、人物和作品                         |
| `/about/methodology/` | 收录标准、核验规则、数据来源和纠错方式                 |

首页采用双入口结构：

- 第一入口是节目，强调最新一期和近期更新。
- 第二入口是作品，提供搜索、筛选和主题探索。
- 第一屏同时提供统一搜索框，不把网站做成只有筛选器的数据库表格。

作品详情页采用证据优先顺序：

1. 原版首图、作品名称、原名、创作者、年份和媒介。
2. 推荐出处，包括期数、节目标题、推荐人、官方证据链接和核验状态。
3. 作品简介和主题标签。
4. 书籍中译本或影视地区版本。
5. 同作者、同导演、同系列和同一期作品。
6. 带理由的相似作品。
7. 数据来源、图片来源和最后核验时间。

书籍才显示译者、出版社、ISBN、删节和翻译质量模块。影视作品使用导演、原始发行信息、地区译名和字幕说明，不套用书籍版本结构。

## 13. 搜索与筛选

搜索索引在构建阶段生成，覆盖：

- 节目编号、标题和简介。
- 嘉宾、作者、导演和译者姓名及其别名。
- 中文名、原名和常见译名。
- 主题、媒介和推荐原文。

搜索结果按实体类型分组，允许直接进入节目、作品、人物或主题。筛选器状态写入 URL 查询参数，便于分享和返回。

构建任务为每个实体输出规范化展示文本、别名、中文双字词元、拉丁单词词元和权重。浏览器下载按实体拆分的压缩索引，先做精确名称和前缀匹配，再做词元交集排序。V1 不引入远程搜索服务，也不在浏览器中运行向量模型。

V1 数据规模使用静态索引。只有出现以下任一条件时才重新评估动态搜索：

- 作品数量超过一万且静态索引显著影响下载或构建时间。
- 需要用户私有数据或权限过滤。
- 需要实时写入后立即检索。

## 14. 状态展示与纠错

公开页面使用清晰状态，不用模糊星级代替证据：

- 已核验：关键字段和推荐关系有来源支持。
- 部分核验：推荐关系成立，但版本或创作者字段仍不完整。
- 待核验：只显示状态提示，不公开高风险候选事实。
- 已排除：仅保留在内部审核历史，不出现在公开搜索中。

每个详情页提供“报告资料错误”链接，指向预填实体 ID 和页面 URL 的 GitHub Issue。提交者不需要接触数据文件。修复通过拉取请求完成并保留修改历史。

## 15. 错误处理

| 故障                 | 行为                                        |
| -------------------- | ------------------------------------------- |
| 官方来源暂时不可访问 | 保留旧快照，任务失败，不覆盖现有公开数据    |
| 外部元数据 API 失败  | 使用最近缓存，新作品保留待核验状态          |
| schema 校验失败      | 阻止构建和发布，输出具体实体 ID、字段和来源 |
| 推荐解析产生歧义     | 写入审核队列，不公开候选结果                |
| 图片失效             | 切换备用来源或本地文字封面，记录待复核状态  |
| 向量服务额度耗尽     | 跳过向量更新，使用结构化推荐                |
| 自动拉取请求检查失败 | 不自动合并，不影响当前线上版本              |

错误日志不得包含 API 密钥、完整环境变量或其他秘密。

## 16. 性能、可访问性和响应式设计

性能原则：

- 页面默认静态输出，交互脚本只用于搜索、筛选和必要的展开组件。
- 列表分页或分段加载，不在首页注入全部作品详情。
- 图片使用响应式尺寸、懒加载和固定宽高比。
- 字体以系统字体和有限的自托管字体为主，不阻塞正文显示。
- 构建输出进行压缩和资源哈希。

可访问性目标为 WCAG 2.2 AA：

- 所有交互可用键盘完成。
- 焦点状态清晰可见。
- 状态不能只靠颜色表达。
- 封面替代文本描述作品和版本，不重复装饰信息。
- 标题层级、表格标题和表单标签语义正确。
- 尊重减少动态效果设置。

移动端保持同样的信息顺序。筛选器折叠为抽屉，证据和版本信息不隐藏为仅桌面可见内容。

## 17. 安全、隐私和成本

- V1 不收集用户账户数据，不接入第三方广告或行为追踪。
- 如需访问量统计，使用无需跨站用户画像的轻量统计方案，并在启用前单独确认。
- API 密钥存放于环境变量和 GitHub Secrets，`.env` 必须被 `.gitignore` 排除。
- 构建日志和静态产物执行秘密扫描。
- 外部链接使用安全的跳转属性，不把来源页面脚本嵌入本站。
- R2 只保存允许镜像的图片和本站生成资产。

免费优先策略：

- 静态访问首先使用 Cloudflare 免费额度。
- GitHub Actions 只处理增量变化，避免无意义地重跑全部外部查询。
- Workers AI 只用于构建期补充信号，额度不足不影响网站。
- 不在 V1 启用 D1、付费搜索或常驻服务器。
- 任何可能产生费用的资源在启用前设置明确用量上限和告警。

## 18. 测试与质量门槛

项目采用测试先行。实现至少包含以下测试层：

| 层级           | 覆盖内容                                                   |
| -------------- | ---------------------------------------------------------- |
| Schema 测试    | 合法和非法实体、枚举、来源字段、发布状态                   |
| 解析器单元测试 | 推荐栏目、多人推荐、一行多作品、无推荐和异常格式           |
| 领域单元测试   | 作品消歧、首图排序、降级、硬关系和相似评分                 |
| 数据质量测试   | 无证据推荐禁止公开、翻译评价来源要求、稳定 ID 和重复项     |
| 集成测试       | 从固定官方快照到规范化 JSON、静态页面和搜索索引            |
| 端到端测试     | 首页搜索、筛选、节目到作品、作品证据、图片降级和移动端导航 |
| 构建检查       | TypeScript、lint、静态构建、链接检查和秘密扫描             |

默认测试不依赖实时第三方网络。外部 API 使用固定响应夹具进行契约测试，另设可手动运行的在线烟雾测试验证当前 API 可用性。

任何自动发布必须通过：

1. TypeScript 类型检查。
2. lint。
3. 单元和数据质量测试。
4. 静态构建。
5. 关键页面 Playwright 端到端测试。
6. 变更文件范围检查。

## 19. 开发与运维命令

仓库采用 Scripts to Rule Them All 风格，所有本地和 CI 命令通过 `script/` 目录提供稳定入口：

| 命令               | 责任                                           |
| ------------------ | ---------------------------------------------- |
| `script/setup`     | 安装锁定依赖并检查必需运行环境                 |
| `script/server`    | 启动本地网站和文件监听                         |
| `script/sync`      | 抓取并生成候选数据，不自动公开高风险字段       |
| `script/typecheck` | 运行 TypeScript 类型检查                       |
| `script/lint`      | 运行代码、Markdown 和数据格式检查              |
| `script/test`      | 运行默认离线测试套件                           |
| `script/build`     | 生成规范化数据、搜索索引和静态站点             |
| `script/ci`        | 按 CI 顺序运行类型、lint、测试、构建和范围检查 |

Windows 本地环境通过 Git Bash 执行这些入口，脚本不得依赖 WSL 路径。脚本内部调用 npm CLI 时使用 `npx`。实现阶段若改变命令或依赖关系，必须同步更新项目 `AGENTS.md`。

## 20. 部署与运行

主分支只接收经过拉取请求检查的变更。部署流程：

```text
拉取请求通过检查并合并
          ↓
生成规范化数据和静态搜索索引
          ↓
构建 Astro 静态站点
          ↓
运行端到端烟雾测试
          ↓
部署到 Cloudflare Workers Static Assets
          ↓
检查首页、最新节目和抽样作品页
```

每次部署保留对应提交 SHA、数据抓取时间和构建时间。部署失败时继续提供上一个成功版本。

## 21. 分阶段交付

V1 分为四个可独立验证的阶段：

1. 数据契约与迁移：建立 schema、稳定 ID、证据模型和审核队列，迁移现有 237 期和 423 条推荐记录。
2. 静态网站核心：完成首页、节目列表与详情、作品列表与证据优先详情、搜索和筛选。
3. 数据增强：接入开放混合 API、A+ 图片层、同作者关系和相似作品排序。
4. 自动同步与公开部署：建立分层拉取请求、自动检查、Cloudflare 部署和运行监测。

每个阶段单独通过测试和页面验收后再进入下一阶段。数据错误不能因为页面尚未显示而被视为无影响。

## 22. V1 验收标准

V1 完成时必须满足：

- 公开网站可以浏览现有全部节目，并显示每期的来源和核验状态。
- 已核验的正式推荐能够从节目页进入规范化作品页。
- 作品页先展示推荐证据，再展示版本、同作者作品和相似作品。
- 相似作品显示明确原因，同作者作品来自确定关系。
- 新一期被发现后，低风险节目字段可以通过受限自动拉取请求发布。
- 未核验推荐、译本和翻译质量不会伪装成确定事实。
- 首图优先使用可核验、可展示且清晰度合格的原版图片。
- 图片来源、许可和降级路径可追溯。
- 外部 API 全部不可用时，已发布页面仍然可访问。
- 仓库中没有硬编码密钥，构建产物不包含秘密。
- 类型检查、lint、单元测试、数据质量测试、静态构建和端到端测试全部通过。
- 桌面和移动端的关键路径均经过浏览器实际验收。

## 23. 实现前约束

本规范批准后才能编写实现计划。实现计划必须把 schema 和数据迁移放在前端页面之前，不能先用现有扁平 JSON 快速拼页面，再把来源和核验状态补回去。

任何改变以下决策的实现都必须先修订本规范：

- 正式推荐的收录标准。
- 分层发布边界。
- 翻译质量证据规则。
- 原版首图优先顺序。
- 第三方图片的镜像权限策略。
- 同作者硬关系和相似排序的区分。
